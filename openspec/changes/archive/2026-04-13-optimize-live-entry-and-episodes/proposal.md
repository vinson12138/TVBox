# 提案：优化主页直播入口与详情页选集体验

## 背景

当前仓库中的直播入口与选集逻辑已经能满足基础播放，但随着站点返回数据复杂度上升，出现了几类持续性的可用性问题：

1. 主页直播入口仅依赖直播配置是否存在来决定显示，缺少面向用户的全局开关。
2. `VideoDetail` 页的选集区主要以单行横向滚动呈现，长剧、动漫、多版本资源浏览成本较高。
3. 选集排序仍主要依赖从标题中提取单个数字，无法稳定识别“第几部 / 第几季 / 第几集 / 画质 / 格式 / 特别篇”等信息。
4. 部分站点或动态补全后的线路中，存在同名重复、近似重复或同一集多版本混杂的问题，导致选集区噪音较大。

这些问题看似分散，实际都集中在同一条链路上：

```text
站点详情返回原始播放串
  -> Vod / Flag / Episode 拆分
  -> 历史记录匹配
  -> 选集排序与分组
  -> 选集 UI 展示
```

如果仅分别修改按钮、列表样式或局部正则，后续维护成本会继续上升。

## 目标

本变更旨在建立一套更稳定的选集组织模型，并据此改进主页与详情页体验。

具体目标：

1. 提供一个全局设置项，用于控制主页是否显示直播入口。
2. 将详情页选集区改造成更适合长列表浏览的横向流动网格方案，而不是单行横向滚动为主。
3. 引入更明确的选集结构化识别能力，为排序、分组、去重提供统一依据。
4. 对重复片源和近似重复选集进行更合理的归类，尽量减少噪音，同时保留必要的多版本信息。
5. 保持历史记录、续播定位、倒序播放等现有核心体验可兼容迁移。
6. 统一选集展示文本与分页口径，减少冗余控件和无效信息。

## 非目标

本提案不包含以下内容：

1. 不改变 Spider / JS / PY / JAR 插件的接口协议。
2. 不在本次变更中重构播放器核心、解析器体系或站点配置协议。
3. 不承诺一次性解决所有站点的命名混乱问题，而是建立可逐步扩展的整理框架。
4. 不在草案阶段直接实施 UI 或数据层代码变更。

## 范围

### 包含范围

1. 主页直播入口显示策略。
2. 手机端与电视端详情页选集区的展示策略。
3. `Vod -> Flag -> Episode` 的选集组织逻辑。
4. 历史记录与选集匹配逻辑的兼容方案。
5. 选集去重、分组、排序的规则定义。

### 暂不纳入

1. 直播页内部的播放或频道组织逻辑。
2. 搜索结果页、收藏页、历史页的列表样式统一改造。
3. 面向配置文件作者的新字段扩展。

## 方案摘要

本变更建议按三层推进：

1. 先增加主页直播入口全局开关，补齐显示策略。
2. 再在数据层建立“选集结构化元信息”，让每个选集除了原始 `name/desc/url` 之外，还能推导出主序号、内容类型、版本标签、排序键和去重键。
3. 最后让手机端和电视端的选集 UI 消费统一的数据结构，实现更清晰的分组、倒序和多版本展示。

## 风险

1. 历史记录目前主要依赖选集名称匹配，若去重和分组策略变化过大，可能影响续播命中率。
2. 部分站点的标题命名极不规整，结构化识别必须允许回退到原始顺序。
3. “去重”与“保留多版本”之间存在天然张力，需要明确产品取舍。

## 已确认决策

1. 主页直播入口默认开启，由用户在设置中手动关闭。
2. 同一集多版本采用“折叠归类优先”的策略，优先减少主选集区噪音。
3. 分组优先级以“正片体验优先”为主，其次再呈现特别篇、花絮、预告等内容。
4. 手机端详情页保留“更多选集”作为补充入口，但主视图切换为横向流动网格。
5. 电视端继续保留分页能力，但以分组优先、分页辅助的方式组织选集。
6. 对于剧集类视频，正片选集默认只显示序号，不显示“第N集”等冗余前缀。
7. 当前两个正序/倒序入口中，仅保留带文字的主按钮；箭头式倒序按钮移除。
8. 带文字的正序/倒序按钮在切换后必须同步更新文本，文本表示当前状态。
9. 分页规则调整为：剧集类正片按 20 集一组，其他内容按 10 个一组。
